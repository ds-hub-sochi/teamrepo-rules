# Реестр использования моделей

Создай воспроизводимый реестр «бизнес-задача → проект → роль модели → конкретная модель → владелец репозитория → свидетельства». Агент должен понять применение по коду и исследовать саму модель. Список найденных названий — только рабочая очередь, не итог анализа.

## До старта

Кратко зафиксируй цель, источники/ветки, ограничения доступа, формат результата и точки проверки. Используй уже заданные пользователем условия, уточняй только влияющие на результат пробелы. По умолчанию анализируй default branch и публичные репозитории; включай доступные закрытые репозитории для внутреннего аудита организации, сохраняя результаты в закрытом месте.

Прочитай [контракт и критерии](references/contract.md). Перед новой реализацией или рекомендацией замены соблюдай применимые правила Reuse Mesh из `teamrepo-rules`; недоступность сервиса явно запиши. Сам аудит не требует установки моделей или выполнения исследуемого кода.

## Сбор

Для GitHub используй `scripts/collect.py` (Python 3.9+, авторизованный `gh`). Все пути ниже задавай относительно корня клона `teamrepo-rules`, либо замени их абсолютными путями к установленному навыку:

```sh
python3 model-usage-audit/scripts/collect.py --org ORGANIZATION \
  --visibility public --output .local/model-audit/inventory.json \
  --cache .local/model-audit/cache
```

`--visibility all` включает доступные приватные проекты. `--repo NAME` ограничивает список; флаг повторяемый. Лимиты `--max-files` и `--max-bytes` ограничивают чтение; `--workers` — параллельные HTTP-запросы. Кэш содержит исходники и должен оставаться закрытым. Не запускай скачанные скрипты, ноутбуки и не десериализуй веса.

Сборщик фиксирует SHA, ссылки на строки, выбранные файлы, ошибки и пропуски. Он выдаёт **кандидатов**, а не полный список моделей. Regex не разрешает динамические имена, внутренние API, импорты собственного класса и произвольные архитектуры. `scanned` означает чтение всех подходящих файлов в заданных форматах, не полноту семантического аудита. Отсутствие кандидатов не означает отсутствие моделей.

## Проверка и обогащение

### 1. Понять бизнес-задачу по коду

Проследи цепочку от входа пользователя/данных до результата: endpoint, CLI или UI → вызывающая функция → предобработка → вызов модели → использование ответа. README поясняет предметную область, но не заменяет чтение цепочки. Читай файлы за лимитом сборщика, пока задача и роль не станут ясны либо не встретится конкретный недоступный участок.

Запиши `business_task` обычным языком: кому и для какого результата помогает модель. «Эмбеддинги», «классификация» и «LoRA» — технические роли, а не достаточное описание бизнес-задачи. Пример: «найти видео нужного жеста по введённому слову, чтобы собрать жестовое видео сообщения». Отдельно запиши `input`, `output`, `role`, `code_trace` и ссылки `business_evidence` на коммит. Если это тест, каталог поддерживаемых моделей или конфигурация эксперимента, явно укажи это.

Объединяй алиасы по свидетельствам. Различай backbone, tokenizer, embedding, adapter и конечные веса. Два checkpoint одного класса с разными задачами — два применения; разверни их через `applications`. Собственная архитектура, адаптация и происхождение конечных весов — разные выводы. Код train/loss/optimizer и связь с артефактом нужны для утверждения о собственном обучении, но отсутствие runtime не мешает объяснить бизнес-назначение кода.

### 2. Выяснить, что это за модель

Для каждого применения найди точный publisher/model ID в коде/конфигах; проверь его на Hugging Face, прочитай model card. Используй доступный HF connector либо `scripts/lookup_models.py`. Если точного совпадения нет, выполни поиск по названию; затем проверь официальный репозиторий/документацию автора. Сохраняй запрос, результат и дату, включая отрицательный результат. Не объявляй закрытой/собственной модель только потому, что поиск ничего не дал.

```sh
python3 model-usage-audit/scripts/lookup_models.py \
  --model sentence-transformers/all-MiniLM-L6-v2 --search MODEL_NAME \
  --cache .local/model-audit/model-cards --output .local/model-audit/model-lookups.json
```

Helper получает метаданные и README, не веса. Передавай публичные имена моделей, не закрытый код или секретные конфиги. Он не пишет смысловую аннотацию: агент читает card и формулирует `model_info.description`, назначение модели, автора, архитектуру, лицензию и доступность весов с источником/датой. Сохрани отдельно **что модель умеет вообще** и **зачем она используется здесь**.

Не подменяй точные веса похожим timm/torchvision checkpoint, API-route — названием произвольной модели, специализированную модель проекта — её базой. При найденной только основе укажи `match_status: base_only`; для неподтверждённого похожего варианта — `related`. В описании явно обозначь границы совпадения.

### 3. Указать ответственного

Ответственный — **владелец GitHub-репозитория**, поле `owner.login` API GitHub. Это может быть организация; не подменяй её автором коммита или CODEOWNERS. Сохраняй `owner_source: github_repository_owner` и ссылку. CODEOWNERS можно оставить дополнительным полем `code_owner`. Применяй правило ко всем записям, даже ещё не разобранным агентом.

Сохрани результаты в JSON overlay по [контракту](references/contract.md). Проверки бизнес-задачи привязаны к `reviewed_commit`, сведения о модели — к URL/model ID/дате и, если доступен, revision model card. При изменении кода перечитай цепочку; не копируй старое назначение без проверки.

## Устаревание и изменения

Разделяй: подтверждённый lifecycle-риск по первоисточнику; инженерный сигнал для проверки; неизвестное. Возраст репозитория и выход более новой модели сами по себе не доказывают устаревание. Для каждого подтверждённого риска нужны модель/версия, официальный источник, дата проверки, применимость к найденному способу использования и конкретный следующий шаг. Примеры: прекращение API, архив upstream, несовместимость среды или неподдерживаемая версия.

Заполняй `lifecycle` в overlay; не превращай отсутствие такой проверки в зелёный статус. Предложение замены должно учитывать метрику качества, latency, hardware, лицензию и регрессионный тест на тех же данных. Модели автоматически не меняй.

## Результат и повторный запуск

```sh
python3 model-usage-audit/scripts/render.py \
  --input .local/model-audit/inventory.json \
  --review .local/model-audit/review.json \
  --output .local/model-audit/dashboard.html
```

HTML автономный. Главный экран показывает разобранные бизнес-применения: задачу, вход/выход, роль, описание модели и владельца репозитория. Общий обзор группируй по бизнес-задачам/проектам; декомпозиция ведёт к модели, model card и цепочке кода. Неразобранные находки доступны отдельно и не увеличивают число разобранных применений. `--review` можно опустить только для промежуточной очереди сбора; не выдавай её за завершённый анализ. Для публичного примера используй `--public-only`; дополнительно проверь overlay и итог на закрытые ссылки и данные. Полный закрытый снимок не добавляй в публичный `teamrepo-rules` и не публикуй в Pages/Sites.

При повторном сборе сохрани предыдущий снимок и передай `--previous PATH` в renderer. Добавления/исчезновения сравниваются только при сопоставимом покрытии, успешном чтении файлов и одинаковом SHA для проверки overlay. Исчезновение кандидата при неполном сканировании не означает отказ от модели. Расписание запуска создавай только по запросу.

## Приёмка

- Список репозиториев пагинирован; знаменатель — доступные текущему аккаунту, не все существующие в организации.
- Каждый вывод имеет ссылку на SHA/файл/строку; ноутбук — SHA/номер ячейки без выдуманного номера строки JSON.
- Для каждой разобранной записи есть бизнес-задача по цепочке кода, вход/выход и роль; отдельно — описание самой модели с результатом поиска и источником. Утверждение «проанализировано» не должно основываться только на regex или model card.
- Ответственный совпадает с владельцем репозитория GitHub; источник назначения виден.
- Есть точные лимиты, ошибки, пустые и частично прочитанные проекты; неизвестные не заменены нулями.
- Сводка, фильтры, детали и экспорт согласованы; проверь населённую выборку, сброс, пустую выборку и узкий экран.
- Существующие правила и исследуемые проекты не изменены; команды воспроизведения и ограничения сохранены в `docs` целевого репозитория. В отчёте назови, что проверено и что ещё требует владельца или runtime-свидетельств.
