# Контракт реестра

## Слои и единица учёта

1. `inventory.json`: неизменяемое свидетельство сканирования, без содержимого строк исходников. Кэш blob содержит исходники и хранится локально.
2. `review.json`: проверка агентом или владельцем с привязкой к SHA. Не редактирует автоматически найденные свидетельства.
3. `dashboard.html`: переносимый результат с раскрытием деталей; наследует чувствительность данных.

Версия схемы — `1`. Поля collector описаны его выходным JSON. `repositories[].usages[].id` — стабильный hash `repository:model.lower()`. Это ID кандидата, не глобальный идентификатор модели. Число кандидатов нельзя называть числом уникальных моделей.

Overlay имеет вид:

```json
{
  "schema_version": 1,
  "reviews": [
    {
      "id": "candidate-id-from-inventory",
      "reviewed_commit": "40-char-commit-sha",
      "canonical_model": "publisher/model-id",
      "task": "Детекция животных на фотоловушках",
      "owner": null,
      "origin": "open_weights",
      "stage": "inference_code",
      "status": "reviewed",
      "revision": null,
      "upstream": "https://huggingface.co/publisher/model-id",
      "license": "unknown",
      "review_evidence": ["https://github.com/ORG/REPO/blob/SHA/inference.py#L12"],
      "lifecycle": {
        "status": "not_checked",
        "checked_at": null,
        "source": null,
        "reason": null,
        "next_step": "Сверить model card и используемый revision"
      }
    }
  ]
}
```

Если один кандидат имеет несколько применений, используй `applications` — непустой массив объектов с `task`, `owner`, `stage`, `review_evidence`; renderer разворачивает их в отдельные строки. `canonical_model` объединяет алиасы только после проверки; ревизии остаются отдельным полем. Не копируй пример как фактическое наблюдение.

Для находок, которые regex не обнаружил, overlay поддерживает `manual_usages`. Каждый элемент содержит те же поля проверки плюс `id` (с префиксом `manual:`), `repository`, `model`, `family` и `evidence` (объекты `path`, `line`, `cell`, `kind`, `context`, `url`). Это позволяет сохранить результат семантического чтения при повторном сборе. Нужны тот же SHA и ссылки на код; при смене SHA ручная находка не применяется, проверку надо повторить.

`origin`: `open_source` (проверены код и лицензия), `open_weights` (доступны веса, не утверждает OSI-совместимость), `custom`, `fine_tuned`, `proprietary_api`, `unknown`. Лицензии кода, весов и данных независимы. Фреймворк и архитектура не определяют лицензию конкретных весов.

Дополнительные проверенные поля: `role` (например, backbone/embedding/reranker/final_model), `base_model` (канонический ID основы), `notes` (границы вывода и связь с артефактом). Не считать backbone и конечный чекпойнт двумя независимыми внедрениями.

`stage`: `documentation`, `configuration`, `experiment`, `training_code`, `inference_code`, `production_verified`, `unknown`. Для `production_verified` приложи датированный лог реального вызова, deployment/runtime evidence и связь с моделью/revision. В текущем renderer runtime-подтверждение принимается только при наличии `runtime_evidence` (непустой массив безопасных ссылок); иначе stage понижается до `inference_code`.

`status`: `candidate` или `reviewed`. Даже reviewed требует привязки к SHA и свидетельств. `lifecycle.status`: `not_checked`, `no_issue_found`, `review_needed`, `deprecated`, `retired`. Последние три — вывод проверяющего; confirmed `deprecated/retired` без первоисточника и `checked_at` отклоняются.

`owner: null` — ответственный неизвестен; репозиторий не заменяет команду. Показывай `code_owner` отдельно. Кандидаты вида `args.model`, локальный путь, номер версии без модели — задачи ручного разрешения, а не дополнительные модели.

Верхнеуровневый `repository_findings` в overlay — отдельные сигналы по подходам/фреймворкам. Поля: `repository`, `reviewed_commit`, `title`, `status`, `reason`, `next_step`, `source`, `checked_at`, `code_evidence` (массив ссылок). Например, deprecated API агента — риск подхода при обновлении зависимости, а не deprecated LLM. Не переносить такой статус на модель. Для старого lockfile явно отделять текущую установленную версию от нового upstream API.

## Общий дашборд и декомпозиция

Обзор: охват доступных репозиториев, число кандидатов/проверенных применений, неизвестные владельцы, очередь lifecycle-проверки. Число моделей считай только по проверенным canonical ID, показывай знаменатель и неизвестные.

Декомпозиция: организация → проект → задача/владелец → модель/revision → свидетельство. Дополнительно обратный срез: модель → все её проекты и задачи. Общие семейства показывай как категории кандидатов, не как точные модели. Отдельно видны ошибки доступа, пустые репозитории, лимит файлов и необследованные ветки.

## Сравнение снимков

Добавление кандидата означает новое обнаружение, не дату внедрения. Исчезновение подтверждай только при сопоставимых версиях сборщика, лимитах, формате и успешном чтении сравниваемых файлов; иначе пометь как «требует перепроверки». Статус prod не выводится из активности GitHub. Для SLA свежести используй согласованный срок, не выдуманный универсальный порог.
